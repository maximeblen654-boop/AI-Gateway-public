# 兼容事实与上线前确认

状态：`RECORDED_COMPATIBILITY / NOT_DEPLOYED`。按用户第三轮审查决定，旧 Core 不兼容属于实际规划上线或旧版本回退前需确认的事实，不自动作为当前开发 P0 或阻断；本轮不开发兼容回退体系，也未完成候选构建或生产发布审核。

## 数据和接口

| 组合/数据 | 实际边界 |
|---|---|
| 新 Core + 新 Bridge/BFF + 新图片 | 首次完整持久化固定72h；receipt/result传原片期限；所有已知 Studio 副本遵守同一截止 |
| 新三组件 + 新视频 | BFF put固定48h，受信capture把原始时间交Core；Core先校验期限才回源 |
| 新组件读取历史 PNG/既有期限 | 具体承诺保留；真正旧图片兼容7天，不以升级/恢复时刻重算 |
| 新组件读取旧视频v1/v2或无新策略的旧单 | `legacy_unknown`，不施加破坏性的48h批量删除 |
| 新任务期限sidecar丢失/损坏 | 永久新策略标记仍在时拒绝，不按legacy重新放行 |
| 旧 Core + 已写 draft.save_receipt 的配置 | 旧严格 reader 无法读取；实际旧版本回退前需确认兼容，当前开发只记录，不删回执或覆盖用户草稿 |
| 旧 Core + 新视频BFF capture字段 | 旧严格请求decoder拒绝result_retention；不能将部分组件混用视为兼容 |
| 旧执行器 + 新期限sidecar/tombstone | 旧执行器不执行新TTL；即使旧JSON能读，也不能宣称下载/恢复期限安全 |

独立 sidecar 和 `json:"-"` 的内存字段避免把本轮期限字段写进旧 image receipt/quote JSON；没有改账务 fingerprint、SQL schema、报价或原订单金额。这个事实不解决旧 Core 的 draft.save_receipt，也不使旧执行器成为合格回退版本。

3. 在隔离固定三组件上验证真实 HTTP 接线、Linux 文件系统与符号链接拒绝、重启、后台调度和跨版本恢复。Windows 符号链接测试因权限限制有1项SKIP，不能写为PASS。

过期媒体字节是按已确认期限可删除的数据；结果哈希、身份、quote/claim、receipt、usage/dedup和财务审计仍保留。不能为恢复下载期限重新生成，也不能为了让未决订单“变绿”伪造捕获或释放。

旧视频兼容处理只形成方案，见 `LEGACY_VIDEO_MIGRATION.md`。没有迁移/批量删除历史视频或扩大永久存储承诺。
