# 批量资金核验与原生运维告警：已确认边界

状态：最终隔离验收已通过；不是部署报告。版本与产物见同目录 HANDOFF.md。

## 复用的资金与任务机制

- `StudioImageRuntime.dispatchExecution` 在供应商 POST 前持久化原任务和每个单元的 claim。
- `recoverExecution` 读取原有响应与原片；缺少可信结果时保留 unknown，不再次调用生成 POST。
- `settle` 验证持久化原片后调用 `SettleQuotedImage -> UsageBillingRepository.Apply`。原生事务把余额、Key/Account 用量、usage 与去重记录共同提交。
- unknown 没有结果时，不进入结算；Studio 图片路径不调用原生批量图片的 reserve/capture/release 接口，因此不是“扣了再退款”，也没有需要释放的预扣。
- 已完成结算后重复回执/恢复沿原去重身份处理，不能再次扣费。

## 需要明确告知的原生边界

unknown 是证据不足，不等于取消或最终失败。若原请求后来取得并保存可信结果，仍允许按冻结报价进行第一次结算。报价过期只阻止新提交，不取消已经提交的原任务。

`deductUsageBillingBalance` 先尝试有余额条件的扣减，余额不足时仍按原生交付后结算合同扣减。因此，等待期间余额被其他任务使用后，迟到的有效首次结算可能形成负余额。这与重复扣费不同。本轮不擅自引入预扣、取消、退款或第二套账本；隔离 PostgreSQL 测试已明确该边界：0.25 余额收到有效的 0.80 首次结算后变为 -0.55；重复同一结算不再扣款，冻结余额始终为零（CI 38662107443），不能宣称“以后绝不会扣费”或“绝无透支风险”。

必须区分两种迟到：客户端超时但原调用仍在执行，或者已持久化原响应但交付/结算未完成，可以通过原任务恢复首次结算；已经结束且 `unit-response.state=unknown` 的502/断线，没有结果文件及供应商单笔查询接口时，当前恢复只保留unknown，不会自动查出结果或产生补扣。unknown本身不触发资金扣减。

没有供应商单笔查询接口时，本轮不会虚构退款证据。没有持久化结果的 unknown 可长期保留原身份，但客户资金占用为零；这不是已确认供应商失败或已完成退款。

## 已复现的监控缺陷及最小修复

1. 持续次数因无数据或进程重启清零后，下一条仍超阈值但尚未达到持续次数的样本，旧代码会把正在告警的事件标记 recovered。修复为只有有效且不超阈值的样本才能恢复；持续次数仍控制新告警。
2. 无请求时错误率/上游错误率显示 0%，容易被理解为健康。改为“无请求样本”，使用中性色。
3. 百分比缺少分母：页面展示同一 SLA 窗口总数、成功数、失败数；新事件在既有 dimensions JSON 中保存触发时请求数、成功/错误/上游错误数和窗口时间，不新增表。
4. 旧 firing 事件的时间不等于连续故障时长，文案改为“尚未确认恢复 · 距触发”。没有新流量不能证明恢复，也不能证明持续故障；不伪造当前状态。

保留 P0/P1 阈值、范围、持续时间和原生告警服务。低流量仍可告警，但必须配合样本数理解。10000 笔持续失败回归保持告警，无数据不自动恢复，有效正常流量可恢复。
